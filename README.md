# TextDiff

Сервис статистического сравнения текстовых корпусов. Специализация темы курса №5
(«Статистический анализ загружаемого набора данных») на текстовых данных.

## Что считаем

Пользователь загружает CSV с текстами, разбитыми на две группы (например, отзывы
«позитивные»/«негативные», тексты двух авторов и т.п.). Ядро строит по каждой группе
лексические статистики (длина текста, лексическое разнообразие TTR, средняя длина слова,
частоты слов) и проверяет гипотезу о различии групп статистическим тестом
(Манна-Уитни или t-тест). На межсессии 1 добавляются регрессия по закону Ципфа и
попарное сравнение текстов по TF-IDF.

## Вход / выход

- **Вход:** CSV (колонки `text`, `group` — имена настраиваются в форме), выбор теста.
- **Выход:** таблица статистик по группам, значение теста и p-value, топ частых слов.

## Реперная точка 21.09

Вход: два числовых списка — TTR (лексическое разнообразие) каждого текста по двум группам
корпуса, плюс число перестановок и seed, заданные в форме.

Ожидаемый выход: наблюдаемая разность средних между группами и p-value — доля перестановок
(из всех возможных либо из случайной выборки), где разность средних не меньше наблюдаемой.

Откуда известен ответ: эталон посчитан вручную, без кода. Для `group_a=[1, 1]`,
`group_b=[3, 3]` пул `[1, 1, 3, 3]` разбивается на все `C(4,2)=6` вариантов по 2+2 элемента.
Наблюдаемая разность средних `|1-3|=2`. Перебором вручную: у разбиений `(1,1)/(3,3)` и
`(3,3)/(1,1)` разность `=2` (не меньше наблюдаемой), у остальных четырёх разбиений —
разность `0`. Значит `pvalue = 2/6`. Тест `test_permutation_test_matches_known_example`
в `core/tests/test_solver.py` сверяет именно это число.

Алгоритм (`core/solver.py:permutation_test`): если общее число разбиений `C(n, na)` не
превышает запрошенное число перестановок — перебираются вообще все разбиения (детерминированно,
`seed` не влияет, ровно как в эталоне); иначе — берётся `n_permutations` случайных перестановок
через `random.Random(seed)`, так что один и тот же `seed` при выборке даёт одинаковый результат
(`test_permutation_test_same_seed_is_reproducible`). Метод подключён в форму как третий вариант
теста («Перестановочный (свой)») и работает на тех же TTR-значениях, что и `mannwhitney`/`ttest`.

Ограничение текущей версии: `Task.params` хранит все строки CSV (`rows`) целиком в JSON-поле —
для учебного объёма это работает, но не масштабируется. До 28.09 нужно вынести содержимое
CSV в отдельное хранилище (файл на диске, `result_file`-подобное поле), оставив в `params`
только ссылку на файл и настройки анализа (колонки, тест, `n_permutations`, `seed`).

Предположительные ошибки:
1. n = 0 приводит к падению расчёта.
В строке h = (b - a) / n возникает деление на ноль.
2. Слишком большое n может надолго загрузить CPU.
Пользователь сам передаёт n, а цикл выполняется n раз. Большое значение может сильно увеличить время расчёта и занять процесс сервера.

Исправленные ошибки:
1. core/solver.py — при полностью одинаковых текстах в группах scipy возвращал NaN вместо числа. NaN — не валидный JSON, SQLite отклонял запись в БД ошибкой IntegrityError.
2. web/views.py — неиспользуемый import json и слишком длинная строка (132 символа при лимите 120) — ruff их не пропускал.
3. tests/test_scenario.py — неправильный порядок импортов (изза этого ruff).

## 30.09

### Пара 11: расчёт в потоке

`web/services.py`: при `USE_QUEUE=0` `create_task` запускает `execute_task` в отдельном потоке и сразу
возвращает задачу со статусом `created` (API отвечает `202`). Статус меняется сам: `created → running → done`
(или `failed`). `templates/web/detail.html` перезагружается (`meta refresh`, раз в 2 секунды), пока статус не
`done` и не `failed`. Решение и его риск — в `docs/adr/004-thread-not-queue.md`.

Замер (`python measure.py`, перестановочный тест, 1000 перестановок, seed = 0):

| текстов | секунд |
|---|---|
| 100 | 0.03 |
| 1000 | 0.33 |
| 4000 | 1.26 |

### Пара 12: плохой вход

`core/schemas.py`: группы — ровно две (иначе `422` с полем `rows`); текст без единого слова (`«123 456 !!!»`)
— `422` с номером строки CSV; строк × перестановок ≤ `LIMIT = 40 000 000`. Три новых теста на плохой вход —
в `tests/test_api.py`.

Границы входа: строк × перестановок ≤ 40 млн (для перестановочного теста) — это около 10 секунд
(замер: 4000 строк × 10 000 перестановок = 40 млн — 12.9 с). Без границы 50 000 строк × 200 000 перестановок —
около 40 минут.

### Пара 13: доступ

Поле `owner` у `Task` существовало и заполнялось и раньше, но нигде не фильтровало: любой пользователь
видел в списке чужие задачи и мог открыть чужую задачу по номеру (и на странице, и в API). Проверено
запуском 30.09 вечером: Пользователь 2 видел «секрет A» Пользователя 1 в списке, на странице и через API.

Исправлено:

- `config/urls.py`: `accounts/` → `django.contrib.auth.urls` (вход/выход), `templates/registration/login.html`.
- `api/api.py`: `NinjaAPI(..., auth=django_auth)` — весь API только после входа, аноним → `401`; список/статус/

### Пара 15: тесты и CI
