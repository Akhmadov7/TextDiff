# TextDiff — статистическое сравнение текстовых корпусов

Веб-сервис, который отвечает на вопрос: **«Различаются ли две группы текстов по лексике — или это случайность?»**
Пользователь загружает CSV с текстами, разбитыми на две группы (позитивные/негативные отзывы, тексты двух авторов и т.п.),
а сервис считает лексические метрики и проверяет гипотезу о различии групп статистическим тестом.

Специализация темы курса №5 «Статистический анализ загружаемого набора данных» на текстовых данных.
Один контракт на два входа: страница (для человека) и `/api/tasks` (для программы).

---

## Идея проекта

По каждой группе текстов ядро считает:

| Метрика | Что означает |
| --- | --- |
| Длина текста | среднее число слов в тексте |
| TTR (type-token ratio) | лексическое разнообразие: уникальные слова ÷ все слова |
| Средняя длина слова | в символах |
| Частоты слов | топ-N самых частых слов корпуса |

Затем проверяется, значимо ли различаются группы (по TTR каждого текста). Доступны три теста:

* **Манна — Уитни** (`mannwhitney`) — непараметрический, по умолчанию;
* **t-критерий Уэлча** (`ttest`) — параметрический;
* **Перестановочный** (`permutation`) — собственная реализация в `core/solver.py`.

**Планы (межсессия 1):** регрессия по закону Ципфа и попарное сравнение текстов по TF-IDF.

## Как работает система

```
Пользователь загружает CSV (форма / POST /api/tasks)
        ↓
Pydantic-схема проверяет вход ДО расчёта (две группы, слова в тексте, лимит нагрузки)
        ↓
Создаётся Task (status = created), владелец — текущий пользователь
        ↓
Расчёт уходит в фоновый поток (или в очередь RQ при USE_QUEUE=1) → ответ 202 сразу
        ↓
Ядро считает статистики и тест: created → running → done / failed
        ↓
Результат сохраняется в Task.result (JSON); страница сама обновляется до готовности
```

Вычислительное ядро (`core/`) **не зависит от Django**: не импортирует его, не ходит в БД и HTTP. Одна точка входа — `run(params) -> dict`.
Слои и правило зависимостей: `views / api → services → core`.

## Вход и выход

**Вход:** CSV в UTF-8 (до 10 МБ) с колонками `text` и `group` (имена настраиваются в форме) + параметры анализа.

| Параметр | По умолчанию | Ограничения |
| --- | --- | --- |
| `test` | `mannwhitney` | `mannwhitney` / `ttest` / `permutation` |
| `top_n` | `20` | 1 … 200 |
| `n_permutations` | `1000` | 1 … 200 000 (только для перестановочного теста) |
| `seed` | `0` | любое целое |
| `rows` | — | от 2 до 50 000 строк, **ровно две группы** |

**Выход:** таблица статистик по группам, значение статистики теста и p-value, топ частых слов, версия ядра и время расчёта.
Для перестановочного теста — ещё число использованных перестановок и способ (точный перебор / случайная выборка).

Пример входа для ядра без веба: `python -m core example_input.json`.

## Эталонный тест (реперная точка 21.09)

**Вход:** `group_a = [1, 1]`, `group_b = [3, 3]`, перестановочный тест.

**Ожидаемый выход:** `pvalue = 2/6 ≈ 0.333`.

**Откуда известен ответ — посчитан вручную, без кода.** Пул `[1, 1, 3, 3]` делится на группы по 2 элемента ровно `C(4,2) = 6` способами.
Наблюдаемая разность средних `|1 − 3| = 2`. У двух разбиений — `(1,1)/(3,3)` и `(3,3)/(1,1)` — разность тоже равна 2, у остальных четырёх — 0.
Значит, `p = 2/6`. Это проверяет тест `test_permutation_test_matches_known_example` (`core/tests/test_solver.py`).

**Алгоритм** (`core/solver.py:permutation_test`):

| Случай | Что делает | Результат |
| --- | --- | --- |
| `C(n, na) ≤ n_permutations` | перебирает **все** разбиения | точный, `seed` не влияет, `p = k / N` |
| `C(n, na) > n_permutations` | случайные перестановки через `random.Random(seed)` | один `seed` — один результат, `p = (k + 1) / (N + 1)` (никогда не 0) |

Если сломать перестановки, краснеет `test_permutation_test_matches_known_example` (перебор и сравнение «не меньше наблюдаемой»)
или `test_sampled_pvalue_never_zero` (случайная выборка и поправка `+1`).

## Замер производительности (пара 11)

Перестановочный тест, 1000 перестановок, `seed = 0`. Замер: `python measure.py`.

| Текстов | Секунд |
| --- | --- |
| 100 | 0.03 |
| 1 000 | 0.33 |
| 4 000 | 1.26 |

**Вывод.** Время растёт линейно. Но у перестановочного теста нагрузка зависит ещё и от числа перестановок, поэтому в схеме есть граница
`строк × перестановок ≤ 40 000 000` (`LIMIT` в `core/schemas.py`). По замеру 4000 строк × 10 000 перестановок = 40 млн — около 13 секунд.
Без границы вход 50 000 строк × 200 000 перестановок считался бы около 40 минут и надолго занял сервер. Расчёт идёт в фоне
(`202` + опрос статуса), а не синхронным ответом.

## Доступ: только свои задачи (пара 13)

Раньше поле `Task.owner` заполнялось, но нигде не фильтровало: любой видел чужие задачи в списке и открывал их по номеру
(проверено 30.09). Теперь доступ закрыт во всех слоях (подробно — `docs/adr/005-access-control.md`):

* `web/views.py` — `@login_required` на списке, форме и странице задачи; выборка только `owner=request.user`;
* `api/api.py` — `NinjaAPI(auth=django_auth)`: весь API только после входа;
* `config/urls.py` — `/accounts/login/` и `/accounts/logout/`, шаблон `templates/registration/login.html`.

| Кто | `/` и `/tasks/new/` | `/tasks/<id>/` | `GET /api/tasks…` | `POST /api/tasks` |
| --- | --- | --- | --- | --- |
| Аноним | `302` → вход | `302` → вход | `401` | `401` |
| Владелец задачи | `200` | `200` | `200` | `202` |
| Другой пользователь | `200` (пустой список) | **`404`** | **`404`** | `202` (своя задача) |

Чужая задача отвечает `404`, а не `403`: посторонний не должен узнать, что задача с таким номером вообще существует.
Своей страницы регистрации нет — пользователя создают `python manage.py createsuperuser` или админка (`/admin/` → Users).

## Плохой вход и безопасность (пары 12 и 14)

Подробный разбор из 8 пунктов — `docs/security_review.md`.

| Находка | Было | Стало |
| --- | --- | --- |
| Расчёт внутри запроса | 2000 строк × 200 000 перестановок → `202` через 66,6 с | расчёт в потоке; такой вход сразу `422` (`LIMIT`) |
| Три группы в CSV | «готово», но `p-value = None` без объяснения | `422` с полем `rows` |
| Текст без слов (`«123 456 !!!»`) | падение расчёта | `422` с номером строки CSV |
| `SECRET_KEY` | запасной ключ в коде | только из `.env`; нет ключа — сервер не стартует |
| `DEBUG` | включён по умолчанию | выключен по умолчанию (`DEBUG=1` в `.env` для разработки) |
| Версии зависимостей | `>=`, `scipy` без версии | все через `==` |

**Принятые риски (не исправлено):**

1. CSV целиком хранится в `Task.params` (JSON) — для учебного объёма работает, но раздувает базу и не масштабируется. План: вынести в файл (`MEDIA_ROOT`), оставив в `params` ссылку и настройки.
2. Разные пределы размера: форма принимает до 10 МБ, API отклоняет тело больше 2,5 МБ (`400` от Django).
3. Поток живёт внутри процесса сервера: при перезапуске задача в статусе `running` навсегда остаётся «считается» (`docs/adr/004-thread-not-queue.md`). Для реальной нагрузки — очередь RQ (`USE_QUEUE=1`).

## Фоновая обработка

`web/services.py`: `create_task` валидирует вход, создаёт `Task` и запускает `execute_task` в отдельном потоке (`daemon=True`);
клиент сразу получает `202`. Поток закрывает своё соединение с БД через `connection.close()`.

Статусы: `created → running → done / failed`. Статус `queued` — только в режиме очереди RQ (`USE_QUEUE=1`, `web/jobs.py`).
Страница задачи (`templates/web/detail.html`) перезагружается каждые 2 секунды, пока статус не `done` и не `failed`.
Решение и его риск — `docs/adr/004-thread-not-queue.md`.

Интерактивная документация (Swagger UI): `/api/docs` (нужен вход).

| Метод | Путь | Коды | Описание |
| --- | --- | --- | --- |

| `GET` | `/api/tasks` | 200 / 401 | Список **своих** задач (до 100), фильтр `?status=` |

## Быстрый запуск

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # Windows: copy .env.example .env
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

* Веб-интерфейс: http://127.0.0.1:8000/ (список задач; нужен вход)
* Форма загрузки: http://127.0.0.1:8000/tasks/new/
* Вход: http://127.0.0.1:8000/accounts/login/
* Документация API: http://127.0.0.1:8000/api/docs
* Админка: http://127.0.0.1:8000/admin/

> `.env` обязателен (и для сервера, и для `pytest`): без `SECRET_KEY` проект честно не запустится.

**Как проверить доступ самому:** первый пользователь — `createsuperuser`, второго создать в `/admin/` → Users. Под пользователем 1 загрузить CSV и запомнить номер задачи.
В окне инкогнито `/` перебросит на вход; войти пользователем 2 и открыть `/tasks/<номер>/` → `404`.

**Docker:** `docker compose up --build` поднимает web, worker, PostgreSQL и Redis (`USE_QUEUE=1`).

## Тесты и CI

| Команда | Что делает |
| --- | --- |
| `pytest -q` | все тесты (23) |
| `pytest core -q` | только ядро (9) |
| `ruff check .` | проверка стиля |
| `python -m core example_input.json` | запуск ядра без веба |

Тесты ядра — `core/tests/test_solver.py` (эталон, воспроизводимость `seed`, равные группы).
Тесты API и сценария — `tests/test_api.py` (9) и `tests/test_scenario.py` (5): создание задачи, `422` на плохой вход, `401` для анонима, «Пользователь 2 не видит задачу Пользователя 1» (и в вебе, и в API), путь «CSV → готово → есть p-value».

CI (`.github/workflows/ci.yml`): на каждый `push` и `pull_request` — Python 3.12, `pip install -r requirements.txt`, `ruff check .`, `pytest -q`.
В CI задан `SECRET_KEY`, потому что `.env` там нет.

**Найденные и исправленные ошибки:**

1. `core/solver.py` — при полностью одинаковых текстах в группах `scipy` возвращал `NaN`. `NaN` — невалидный JSON, SQLite отклонял запись ошибкой `IntegrityError`. Теперь одинаковые группы дают `p = 1.0`, а `NaN` заменяется на `None`.
2. `web/views.py` — неиспользуемый `import json` и слишком длинная строка (132 символа при лимите 120): `ruff` их не пропускал.
3. `tests/test_scenario.py` — неправильный порядок импортов (из-за этого тоже краснел `ruff`).

## Архитектурные принципы

1. `core/` не импортирует Django, не обращается к БД и HTTP.
2. Views и API не содержат бизнес-логики — только вызывают `web/services.py`.
3. Вход валидируется Pydantic-схемой до расчёта. Никакого `eval`/`exec` на пользовательских строках.
4. Статусы задачи меняются только в `services.execute_task` / `jobs.enqueue_task`.
5. Секреты — только в `.env`, в git он не попадает.
6. Любое изменение схемы БД — через миграцию.
