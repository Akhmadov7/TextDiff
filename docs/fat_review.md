# Самопроверка TextDiff на «толстые» функции

Документ проверяет фактическое разделение ответственности в проекте TextDiff.
Проверка относится к рабочему коду; `web/views_fat_example.py` — учебный антипример и не подключён в маршрутах.

| # | Проблема | Почему это плохо | Где должна быть ответственность | Состояние в TextDiff |
|---|---|---|---|---|
| 1 | View или API выполняет статистический расчёт | HTTP-слой становится трудно тестировать и переиспользовать | `core/solver.py` через сервис | Нет. `web/views.py` вызывает `web.services`, а `api/api.py` вызывает `services.create_task()`. Вычисления выполняет только `core.run()`. |
| 2 | Ядро зависит от Django, БД или HTTP | Ядро нельзя запустить отдельно от веб-приложения | `core/` должен быть чистым | Нет. В `core/schemas.py` и `core/solver.py` нет импортов Django; ядро принимает `dict` и возвращает JSON-совместимый `dict`. |
| 3 | Проверка входных данных смешана с расчётом или отсутствует | Ошибочные данные доходят до статистического алгоритма | `core/schemas.py` до запуска ядра | Нет. `TextDiffParams` проверяет строки, группы, имя теста и `top_n`; API возвращает 422 при некорректных параметрах. |
| 4 | Расчёт меняет статус задачи или сохраняет данные сам | Чистая функция получает побочные эффекты | `web/services.py` и `web/jobs.py` | Нет. `services.execute_task()` меняет `running`, `done` и `failed`; `jobs.enqueue_task()` устанавливает `queued`. `core.run()` ничего не сохраняет. |
| 5 | Одна функция одновременно обрабатывает HTTP, CSV, БД и статистику | Нарушается принцип единственной ответственности | Разделить по слоям | Нет. CSV разбирает `services.parse_csv_file()`, задача создаётся в `services.create_task()`, а статистика считается в `core/solver.py`. |

## Пограничный случай: `execute_task`

`web/services.py::execute_task()` выполняет несколько последовательных действий: получает задачу, меняет её статус, вызывает ядро, сохраняет результат или ошибку. Это допустимо, потому что функция является оркестратором сценария выполнения задачи.

Она не содержит алгоритмов обработки текста, не формирует HTTP-ответ и не разбирает CSV. Поэтому её ответственность остаётся одной: управлять жизненным циклом расчётной задачи.

## Учебный антипример

`web/views_fat_example.py::fat_integrate()` специально оставлен вне `urls.py` для разбора архитектурных ошибок. В нём одновременно есть чтение HTTP-параметров, `eval`, вычисление, создание `Task` и HTTP-ответ. В рабочем сценарии TextDiff этот файл не используется.

## Итог

Рабочий поток проекта разделён так:

```text
HTML form / REST API → web.services → core.run → Task в БД → HTML / JSON
```

Это позволяет тестировать ядро отдельно, а веб-слой — через Django-тесты, не смешивая вычислительную и инфраструктурную логику.
