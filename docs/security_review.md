## 1. Расчёт в запросе

**Где:** `web/services.py`, вызов `execute_task` прямо из `create_task`.
**Что нашли:** 2000 строк × 200 000 перестановок → ответ `202` через 66,6 секунды: сервер занят расчётом,
запрос висит. Граница «строк × перестановок» в схеме была, но слишком большая — она ничего не ограничивала.
**Чем грозит:** один пользователь надолго занимает процесс сервера (отказ в обслуживании).
**Что сделали:** `execute_task` запускается в потоке (`web/services.py:53`, ADR-004) — запрос отвечает сразу, статус
меняется сам. Граница выбрана по замеру: `LIMIT = 40 000 000` в `core/schemas.py:7` (4000 строк × 10 000
перестановок = 40 млн считаются около 13 секунд). 2000 × 200 000 теперь отклоняется сразу с `422`.
**Остаточный риск:** поток живёт внутри процесса сервера; при перезапуске задача навсегда остаётся в статусе
`running` (описано в ADR-004). Для настоящей нагрузки нужна очередь (`USE_QUEUE=1`).

## 2. Три группы

**Где:** `core/solver.py:103` — тест считается, только если групп ровно две.
**Что нашли:** три группы → задача «готово», `statistic` и `pvalue` равны `None`, объяснения нет.
**Чем грозит:** пользователь получает «успех» без результата и не понимает почему.
**Что сделали:** `core/schemas.py:28` — групп должно быть ровно две, иначе `422` с полем `rows`
(для формы — ошибка на странице). Проверка стоит в схеме, поэтому одинаково работает для формы и API.

## 3. CSV в базе данных

**Где:** `web/views.py:23` → `web/services.py:46` — все строки CSV кладутся в `Task.params`.
**Что нашли:** CSV 9,3 МБ целиком в `params` (поле формы пропускает до 10 МБ), `db.sqlite3` вырос до 52,6 МБ.
**Чем грозит:** база растёт намного быстрее самих загрузок, медленнее выборки и бэкапы, легко забить диск.
**Что сделали:** ничего — в этот раунд не входило. **Статус: открыт, принят как риск.**
**План:** сохранять CSV файлом в `MEDIA_ROOT` (как требует `AGENTS.md`, п. 6), в `params` оставить ссылку на файл
и настройки анализа.

## 4. Разные пределы размера

**Где:** `web/forms.py:32` (форма — до 10 МБ) и настройка Django `DATA_UPLOAD_MAX_MEMORY_SIZE` (по умолчанию 2,5 МБ).
**Что нашли:** через API тело больше 2,5 МБ → `400` от Django, а не `422` от нашей схемы; через форму можно
загрузить до 10 МБ. Пределы не согласованы, ответы разные.
**Чем грозит:** непредсказуемое поведение на границе, клиент API получает ошибку не в нашем формате.
**Что сделали:** ничего — в этот раунд не входило. **Статус: открыт, принят как риск.**
**План:** выбрать один предел и описать его в README; либо поднять `DATA_UPLOAD_MAX_MEMORY_SIZE`, либо
принимать файл, а не JSON-тело.

## 5. Запасной SECRET_KEY

**Где:** `config/settings.py:20`.
**Что нашли:** `os.environ.get("SECRET_KEY", "dev-only-insecure-key-change-me")` — если ключ забыли задать,
сервер молча стартует с ключом, который лежит в открытом коде.
**Чем грозит:** подделка сессий и подписанных данных у любого, кто прочитал репозиторий.
**Что сделали:** `os.environ["SECRET_KEY"]` без запасного значения — нет ключа, сервер не запускается.
Ключ берётся из `.env` (есть в `.env.example`); в CI задан отдельный ключ в `.github/workflows/ci.yml`.
**Остаточный риск:** `docker-compose.yml` (строки 22 и 33) по-прежнему подставляет `dev-only-insecure-key`,
если `SECRET_KEY` не задан. Это учебный compose; перед настоящим запуском ключ нужно задать.

## 6. DEBUG по умолчанию

**Где:** `config/settings.py:21`.
**Что нашли:** `DEBUG` по умолчанию `"1"` — если переменную забыли, на сервере включён режим отладки.
**Чем грозит:** страницы ошибок показывают код, настройки и переменные окружения.
**Что сделали:** по умолчанию `DEBUG` выключен (`"0"`), включается только явно: `DEBUG=1` (в `.env.example` оно есть,
для разработки достаточно скопировать файл).

## 7. Версии зависимостей

**Где:** `requirements.txt`.
**Что нашли:** все пакеты через `>=`, а `scipy` — без версии вообще.
**Чем грозит:** сборка завтра может отличаться от сегодняшней (CI «внезапно» красный, поведение теста меняется
после обновления), в образ может попасть версия с уязвимостью.
**Что сделали:** все пакеты закреплены через `==` (`Django==5.2.17`, `scipy==1.17.1` и т. д.). Проверено: в чистом
окружении Python 3.12 (как в CI) установка проходит, `ruff` и `pytest` зелёные; те же версии есть для Python 3.14 (Dockerfile).
**Остаточный риск:** закреплены только прямые зависимости (`numpy`, `sqlparse` и др. подтягиваются сами).

## 8. Проверено и в порядке

Менять не пришлось, проверено запуском 01.10:
- **Экранирование.** `<script>alert(1)</script>` в названии задачи и в названии группы CSV на странице задачи
  выводится как `&lt;script&gt;…` — Django экранирует вывод в шаблонах, `|safe` и `mark_safe` в коде нет.
- **`.env.example` есть**, секреты в код не кладутся (кроме запасного ключа из пункта 5, он исправлен).
- **В git нет лишнего:** `.gitignore` закрывает `.env`, `db.sqlite3`, `media/`, `staticfiles/`, `__pycache__/`,
  `.venv/`, кеши.
- **404 вместо 403:** чужая и несуществующая задача дают одинаковый `404` (и на странице, и в API) — не раскрываем,
  что задача с таким номером есть (ADR-005). Аноним в API получает `401`, в вебе — редирект на вход.
- **Сырого SQL нет:** в коде нет `.raw()`, `.extra()`, `cursor()`; везде ORM.
