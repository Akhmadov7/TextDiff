# ADR-005. Доступ: задача видна только своему владельцу

**Статус:** принято
**Дата:** 2026-10-01

## Контекст
Поле `owner` у `Task` существовало и заполнялось (`web/views.py`, `api/api.py`) с самого начала,
но нигде не использовалось для фильтрации. Список задач (`web/views.py:9`, `api/api.py:51`) отдавал
**все** задачи всех пользователей, а страница и API-эндпоинты задачи (`web/views.py:36`, `api/api.py:59`,
`:64`) открывали любую задачу по номеру через `get_object_or_404(Task, pk=...)` без проверки владельца.
Входа в веб-часть не было вообще — `task_list`/`task_create`/`task_detail` были доступны анонимно.
Проверено запуском 30.09: Пользователь 2 видел чужую задачу («секрет A») и в списке, и на странице,
и через API.

## Рассмотренные варианты
1. **Ничего не менять** — неприемлемо: это утечка чужих данных (результатов анализа) кому угодно,
   кто знает или подбирает номер задачи.
2. **Проверка владельца только на уровне шаблона** (скрывать ссылку, но не закрывать сам URL) —
   не защита: страница и API всё равно отдают данные при прямом переходе по ссылке.
3. **Фильтрация на уровне запроса к БД + обязательный вход** — закрывает доступ на том же уровне,
   где он открывается (ORM-запрос), а не только в интерфейсе.

## Решение
Выбран вариант 3.

- **Веб (`web/views.py`)**: `@login_required` на `task_list`, `task_create`, `task_detail`
  (анонимный пользователь перенаправляется на `/accounts/login/?next=...`).
  `task_list` — `Task.objects.filter(owner=request.user)[:50]`.
  `task_detail` — `get_object_or_404(Task, pk=pk, owner=request.user)` (чужая задача → 404,
  не 403 — чтобы не подтверждать посторонним даже сам факт существования задачи с таким id).
  `task_create` — `owner = request.user` без `else None` (вошедший пользователь гарантирован
  декоратором, ветку для анонима убрали).
- **Вход**: `path("accounts/", include("django.contrib.auth.urls"))` в `config/urls.py` — даёт
  стандартные `django.contrib.auth` вьюхи (`/accounts/login/`, `/accounts/logout/`) без написания
  своих. Шаблон — `templates/registration/login.html` (имя шаблона, которое `LoginView` ищет
  по умолчанию). `LOGIN_URL` в `config/settings.py` указывает на `/accounts/login/`.
- **API (`api/api.py`)**: `NinjaAPI(..., auth=django_auth)` — сессионная аутентификация на уровне
  всего API разом, без декоратора на каждый эндпоинт. Анонимный запрос к любому `/api/...` → 401
  ещё до того, как выполнится тело функции. `list_tasks`/`get_task`/`get_result` — фильтр
  `owner=request.user`; `create_task` — `owner = request.user` без `else None`.

## Последствия
Задача видна только тому, кто её создал. Чужой номер задачи — везде 404 (и на странице, и в API),
а не 403: внешне неотличимо от «такой задачи не существует», что не подтверждает посторонним
даже сам факт её существования. Админка (`/admin/`) продолжает показывать все задачи всем
сотрудникам с доступом в неё — это осознанно: админка — инструмент персонала, а не часть
пользовательского доступа, и её ограничение не входило в эту задачу.
Побочный эффект: `python -m core` и прямые вызовы `core.run()` по-прежнему работают без какой-либо
аутентификации — это ожидаемо, ядро не знает о пользователях и в этом слое их быть не должно.
